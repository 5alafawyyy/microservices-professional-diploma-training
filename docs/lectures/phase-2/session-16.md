## 2. Core concepts

- Resource Requests vs Limits (course table): Requests = "Scheduling guarantee — node has this much available"; purpose row: HPA interaction "HPA calculates: actual CPU / requested CPU"; CPU unit "millicores: 100m = 0.1 CPU". Limits = "Hard cap — CPU throttled, Memory OOMKilled"; HPA interaction "HPA ignores limits entirely"; CPU unit "millicores: 500m = 0.5 CPU". Not-set consequences: no requests → "Pod scheduled anywhere (uncontrolled)"; no limits → "Pod has unlimited access (noisy neighbor)".
- Continue deck simple rule: "request answers 'How much should Kubernetes reserve for scheduling?' Limit answers 'How much may this container consume?'" Request = amount Kubernetes uses when scheduling the Pod (scheduling/capacity planning); Limit = maximum resource amount the container is allowed to consume (resource control).
- CPU: 1000m is approximately one CPU core; exceeding a CPU limit can result in throttling. Memory: if a container exceeds its memory limit it can be terminated and Kubernetes may report OOMKilled; "Memory therefore needs careful sizing for JVM applications."
- Noisy neighbor (continue section 8): "a workload that consumes excessive shared CPU or memory and negatively affects other workloads." Example chain: product-service → excessive CPU/memory → order-service becomes slow → shared cluster unpredictable behavior. "Requests and limits do not create new capacity, but they give Kubernetes better scheduling information and enforce resource constraints."
- The `-Xmx` rule (course): "WARNING: memory limit must be > JVM heap size. Set -Xmx to 70% of memory limit to leave headroom for OS/JVM overhead. Example: limit 768Mi → -Xmx538m."
- HPA — "The CPU Feedback Loop" (course): chain Metrics Server (reads actual CPU usage per pod) → HPA Controller (calculates avg utilization vs target) → Deployment (updates replica count) → New Pods (readiness probe gates traffic ← S15). SCALE OUT: CPU utilization ≥ 70% for 30s → add pods. SCALE IN: CPU utilization < 50% for 300s (5 min cooldown) → remove pods. "The cooldown prevents thrashing: don't remove pods immediately after a spike subsides." Formula: `desired replicas = ceil(currentReplicas × utilization/target)`.
- HPA is a feedback loop, not an instant switch (continue section 19): metrics are collected, HPA evaluates them, the Deployment replica count changes, new Pods are scheduled and started, and readiness checks must pass.
- HPA terms (continue section 18): `scaleTargetRef` (the Deployment whose replica count HPA changes); `minReplicas`; `maxReplicas`; `metric` (the measurement used for scaling); `averageUtilization` (target average CPU utilization relative to CPU requests).
- Metrics Server (continue section 14): "a Kubernetes add-on that collects basic resource usage information from Kubelets and exposes it for components such as HPA and commands such as kubectl top." Comparison table: Metrics Server = basic CPU/memory resource metrics → HPA and kubectl top; Prometheus = general metrics collection/querying/alerting → observability later. "Metrics Server and Prometheus are not the same tool."
- CPU utilization and HPA (continue section 16): "For a CPU-based HPA, utilization is normally calculated relative to CPU requests. Therefore CPU requests are important when using a CPU utilization target."
- Horizontal vs Vertical scaling (continue section 12): Horizontal = number of Pods (2 Pods → 5 Pods); Vertical = resources per Pod (256Mi → 512Mi memory). "For stateless Spring Boot services, horizontal scaling is often a natural Kubernetes strategy."
- HPA limitations (continue section 21): HPA cannot create new Kubernetes nodes; needs usable metrics; does not make every stateful workload safe to scale horizontally; cannot guarantee zero latency during sudden traffic spikes; cannot fix database bottlenecks, connection-pool limits, or application-level bottlenecks; does not replace readiness/liveness/startup configuration. "Node autoscaling and deeper workload tuning are separate concerns."
- Helm purpose in S16 (course): "Our course: raw manifests in S14-S15 (learn the primitives). Helm in S16 (package them). Both coexist in the repo." Continue deck section 22: "Session 15 introduced Helm. Session 16 uses Helm to make resource and autoscaling configuration reusable."
- Raw vs Helm — design choice table (course, question → answer): 1-2 services, team owns all manifests → Raw manifests (simpler); 5+ services with shared config values → Helm (parametrize once, reuse everywhere); need deployment version rollback → Helm (helm rollback tracks history); team new to K8s → Raw manifests first — learn primitives; multiple environments (dev/staging/prod) → Helm (different values.yaml per env); ArgoCD manages deployments → Either works — Helm is a natural fit; one-off debug deployment → Raw manifests (kubectl apply).
- Raw vs Helm — course rule (continue section 24): Raw = small/static deployment, maximum direct YAML visibility, one-off resource; Helm = repeated patterns across services/environments, parameterized images/resources/HPA, reusable packaging and release management. "Course rule: Start simple; use Helm when repetition appears. / Prefer Helm for the growing platform. / Do not template just for the sake of templating."
- RBAC — why permissions matter (continue section 25): "A Pod can run with a Kubernetes identity called a ServiceAccount. Kubernetes RBAC controls what that identity may do. Least privilege means: a service receives only the Kubernetes API permissions it actually needs."
- "Does Every Spring Boot Service Need RBAC?" (continue section 31): "No. Many Spring Boot microservices never call the Kubernetes API. If product-service only talks to PostgreSQL, Redis, Kafka, other services, and external APIs, it may need no Role at all. The correct rule is: give every workload an explicit identity when appropriate, but grant Kubernetes API permissions only when required."
- Least-privilege contrast (course, "The Chart Needs a ServiceAccount"): "The chart deploys product-service as a pod. That pod may need to call the K8s API to read its own ConfigMap at runtime. We need a ServiceAccount and permissions — watch how the chart includes RBAC automatically." Without a dedicated SA: "Pod runs as 'default' ServiceAccount — may have broad cluster permissions (dangerous if compromised)". With `product-service-sa`: "Pod can ONLY read ConfigMaps/Secrets in its namespace" (the comparison line reads "Compromise ≠ cluster write access" — i.e. a compromise does not give cluster write access).
- Namespaces (continue section 34): ecommerce-dev = developer testing; ecommerce = integration/staging; ecommerce-prod = production. "Namespaces help organize resources and apply policies, but they are not a complete security boundary by themselves."
- ResourceQuota and LimitRange — awareness (continue section 36): ResourceQuota can limit aggregate namespace consumption; LimitRange can provide defaults or constraints for individual resources; "These mechanisms complement Pod-level requests and limits."
- Spring Boot readiness + HPA (continue section 38): "HPA may create new Pods, but traffic should only reach Pods that are ready. A Spring Boot application may need time to start the JVM, initialize the application context, connect to dependencies, and become ready." Checklist: resource requests/limits; readiness probe; appropriate startup/liveness strategy; HPA; rolling update settings; application metrics and logs.
- Phase 2 retrospective (course): S9 Docker → 8 services containerized — reproducible environment; S10 Unit + Integration → Testing Pyramid + TestContainers real PostgreSQL; S11 Contract + Chaos → Pact contracts + WireMock + validated Circuit Breaker; S12 Saga Orchestration → OrderSagaOrchestrator + explicit SagaState control; S13 CI Pipeline → GitHub Actions: test → build → push, every push tested; S14 GitOps + Canary → ArgoCD = Git as Source of Truth, drift detection; S15 K8s Core → Probes self-heal deadlocks, Secrets protect passwords; S16 K8s Advanced → HPA scales automatically, Helm packages + versions.

## 5. Important terminology

- Requests — "the amount Kubernetes uses when scheduling the Pod" (scheduling/capacity planning).
- Limits — "maximum resource amount the container is allowed to consume" (resource control); exceeded CPU → throttled; exceeded memory → OOMKilled.
- OOMKill — pod terminated for exceeding a memory limit (incident: 350Mi loaded into 256Mi limit).
- Noisy neighbor — "a workload that consumes excessive shared CPU or memory and negatively affects other workloads."
- Millicores — CPU unit; "1000m is approximately one CPU core"; "100m = 0.1 CPU", "500m = 0.5 CPU".
- HPA (HorizontalPodAutoscaler) — "changes the desired replica count based on observed metrics."
- scaleTargetRef, minReplicas, maxReplicas, metric, averageUtilization — the five HPA terms (continue section 18); averageUtilization is "target average CPU utilization relative to CPU requests."
- Stabilization window — `behavior.scaleDown.stabilizationWindowSeconds: 300` / `behavior.scaleUp.stabilizationWindowSeconds: 0`; "A common idea is to react faster to increasing demand but wait longer before reducing capacity." Course issues slide: `behavior.scaleUp.stabilizationWindowSeconds: 60` to avoid over-reacting.
- Feedback loop (not instant switch) — metrics collected → HPA evaluates → replica count changes → pods scheduled/started → readiness must pass.
- Metrics Server — "a Kubernetes add-on that collects basic resource usage information from Kubelets."
- Chart / Chart.yaml / values.yaml / templates — Helm packaging: chart metadata (name, version), "default configurable values", `{{ .Values.* }}` parametrization; "values.yaml — The Parametrization Contract" (course).
- Release / revision / rollback — `helm list` shows REVISION 2, STATUS deployed, CHART `product-service-0.1.0`; `helm rollback product-service 1` reverts to revision 1.
- ServiceAccount — "an identity used by a workload running in Kubernetes."
- Role — "defines permissions within one namespace."
- RoleBinding — "connects the Role to an identity such as the ServiceAccount."
- ClusterRole — "cluster-wide or reusable cluster-scoped permissions"; "Do not use ClusterRole simply because it is easier. Prefer namespace-scoped permissions when possible."
- Verbs — get, list, watch, create, update, patch, delete; "Grant only the verbs required by the application."
- Least privilege — "a service receives only the Kubernetes API permissions it actually needs."
- ResourceQuota / LimitRange — "limit aggregate namespace consumption" / "provide defaults or constraints for individual resources."
- Immutable image tag — homework requires it (`sha-a81c92d` style); course CI override `sha-abc1234`.
- Phase 2 / Phase 3 — Phase 2 = 8 sessions (S9–S16), "20 Hours", "Full Delivery Pipeline Active"; Phase 3 = Sessions 17–24.

## 8. Failure scenarios

- Traffic spike → OOMKill → cascading failure (course, the opening incident): 10x traffic in 5 min; 256Mi request = 256Mi limit; 350Mi cache load → LIMIT EXCEEDED → OOMKill; 50% traffic to the survivor → 100% CPU → timeouts → P99 8s; no HPA → 22-minute incident. Three compounding failures: limits too tight, no HPA, requests not set.
- CPU limit exceeded → throttling; memory limit exceeded → container terminated and reported OOMKilled ("Memory therefore needs careful sizing for JVM applications").
- Noisy neighbor: one workload's excessive CPU/memory makes another service slow and the shared cluster unpredictable.
- HPA TARGETS: `<unknown>/70%` → "Metrics Server not installed — minikube addons enable metrics-server"; continue guide adds: check Metrics Server, verify CPU requests exist, inspect HPA events.
- HPA never scales (continue troubleshooting): check current CPU, target threshold, min/max replicas, metrics, and whether the workload actually consumes CPU.
- Helm install: `'cannot re-use a name'` → "A release already exists — helm upgrade instead, or helm uninstall first."
- Helm template renders empty ServiceAccount → "Check values.yaml structure: serviceAccount.create: true (nested correctly)."
- HPA scales to maxReplicas immediately → "Add behavior.scaleUp.stabilizationWindowSeconds: 60 to avoid over-reacting."
- Role created but pod gets `'Forbidden'` → "Check RoleBinding subjects match ServiceAccount name + namespace exactly"; continue guide adds checking ServiceAccount, Role, RoleBinding, namespace, resource, and verb.

## 9. Trade-offs

- Requests vs limits: requests = scheduling guarantee (node has this much available) but "Pod scheduled anywhere (uncontrolled)" when unset; limits = hard cap preventing noisy-neighbor behavior but CPU throttling / memory OOMKilled when too tight. "If not set" consequences are asymmetric: no request → uncontrolled placement; no limit → "Pod has unlimited access (noisy neighbor)."
- HPA interaction asymmetry: "HPA calculates: actual CPU / requested CPU" vs "HPA ignores limits entirely" — sizing requests correctly matters because the HPA math uses them.
- minReplicas/maxReplicas: min 2 "always run minimum 2 for availability" vs max "hard cap — prevent runaway scaling costs" (course wording).
- Scale out fast vs scale in slow: "react faster to increasing demand but wait longer before reducing capacity"; 30s scale-out window vs 300s (5 min) scale-in cooldown — "The cooldown prevents thrashing: don't remove pods immediately after a spike subsides." Counter-trade-off: `behavior.scaleUp.stabilizationWindowSeconds: 60` if HPA "scales to maxReplicas immediately ... to avoid over-reacting."
- Horizontal vs vertical scaling: 2→5 pods vs 256Mi→512Mi; "For stateless Spring Boot services, horizontal scaling is often a natural Kubernetes strategy."
- HPA boundaries (continue section 21): cannot create nodes; needs usable metrics; not safe for every stateful workload; no zero-latency guarantee; cannot fix DB/connection-pool/app bottlenecks; does not replace probes — "Node autoscaling and deeper workload tuning are separate concerns."
- Raw manifests vs Helm (course decision table): raw = simpler for 1-2 services and one-off debug deployments; Helm = parametrize once/reuse everywhere for 5+ services with shared config, rollback history, per-env values.yaml; "Team new to K8s? Raw manifests first — learn primitives"; "ArgoCD manages deployments? Either works — Helm is a natural fit."
- Course rule (continue): "Start simple; use Helm when repetition appears. Prefer Helm for the growing platform. Do not template just for the sake of templating."
- RBAC breadth vs convenience: "Do not use ClusterRole simply because it is easier. Prefer namespace-scoped permissions when possible"; dedicated SA = "Pod can ONLY read ConfigMaps/Secrets in its namespace" vs default SA "may have broad cluster permissions (dangerous if compromised)"; but also "Does every Spring Boot service need RBAC? No" — "it may need no Role at all"; "rbac.create: false" default is "a useful safety pattern."
- Metrics Server vs Prometheus scoping: basic CPU/memory metrics for HPA and kubectl top vs general collection/querying/alerting for observability later — "not the same tool."
- Namespaces: logical separation and policy grouping, "but they are not a complete security boundary by themselves."
- Teaching values caveat: resource numbers are "teaching values, not production sizing recommendations"; "Start with measurements and load tests, then tune." HPA behavior values: "Treat these as tuning examples. Production values should be based on workload behavior."

## 13. What I must understand

- Why requests and limits solve different problems: scheduling/capacity planning vs resource control; "Requests and limits do not create new capacity, but they give Kubernetes better scheduling information and enforce resource constraints."
- Why CPU requests are the HPA's denominator: "For a CPU-based HPA, utilization is normally calculated relative to CPU requests"; limits only cap consumption and are ignored by the calculation.
- Why HPA is a feedback loop, not an instant switch: metrics collection, evaluation, replica change, pod scheduling/startup, and readiness all take time; "HPA is not an instantaneous response to every traffic spike"; it cannot guarantee zero latency during sudden spikes.
- Why the scale-in cooldown exists: prevents thrashing — "don't remove pods immediately after a spike subsides."'
- Why horizontal scaling is the natural Kubernetes strategy for stateless Spring Boot services, and why stateful workloads are not automatically safe to scale horizontally.
- Why the OOMKill incident had three compounding failures and how each fix (sizing limits, HPA, setting requests) addresses one layer.
- Why HPA depends on Metrics Server and why "If kubectl top does not work, fix the metrics source before troubleshooting the HPA."
- Why Helm exists in this course: "Learn the primitives" with raw manifests, then "package them"; parametrization contract via values.yaml; `helm rollback tracks history`; per-environment values.yaml; "Do not template just for the sake of templating."
- Why the chart conditionally gates ServiceAccount/Role/HPA: same chart "can therefore enable or disable autoscaling per environment"; `rbac.create: false` default is a safety pattern.
- Why least privilege matters: default SA "may have broad cluster permissions (dangerous if compromised)" vs dedicated SA that "can ONLY read ConfigMaps/Secrets in its namespace"; compromise does not equal cluster write access.
- Why namespaces are isolation but "not a complete security boundary by themselves"; ResourceQuota (aggregate namespace consumption) and LimitRange (defaults/constraints per resource) complement Pod-level requests/limits.
- Why traffic must only reach ready pods: "HPA may create new Pods, but traffic should only reach Pods that are ready" (JVM start, context init, dependency connections); HPA complements, never replaces, readiness/liveness/startup probes.
- Why GitOps owns Helm values: the GitOps repository updates Helm values → Argo CD detects the Git change → Helm renders desired resources → pods; "Argo CD reverts a manual change — That is expected for GitOps-managed resources. Change the Git desired state instead."
- How Session 16 completes Phase 2: the retrospective chain S9→S16 and the end-to-end pipeline (code → production in minutes, with audit trail, rollback, drift detection).
